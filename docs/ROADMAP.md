# 饮食软件产品 Roadmap

## 1. 产品发展路径

v0.2：v1.0 正式发布准备阶段
→ v1.0：第一套可长期使用的正式版本
→ v1.x：记录效率与用户体验优化
→ v2.0：多 Mode 生活记录平台
→ v3.0：离线优先与 App 化
→ v4.0：AI 个人助手
→ v5.0：个人知识数据库

## 2. 版本关系

- 当前处于 `v0.2` 开发阶段。
- `v0.2` 是正式发布 `v1.0` 前的最后一个完整开发阶段。
- 本 Roadmap 列出的全部 v0.2 功能，都必须在 v1.0 发布前完成。
- v0.2 全部完成并通过上线验收后，软件正式发布为 `v1.0`。
- v0.2 已确认的核心功能不得推迟到 v1.x。

## 3. v0.2：v1.0 正式发布准备阶段

### 阶段核心目标

完成软件第一套可以正常长期使用的“记录、规划、执行”闭环。

v0.2 完成后，用户需要能够：

1. 使用现成的公共食品数据库。
2. 管理个人食品。
3. 规划未来一周。
4. 为每一天选择工作、学习、训练、休息或自定义类型。
5. 填写影响当天安排的重要事件和固定时间点。
6. 选择自己的饮食、训练和日程需求。
7. 自动生成未来一周每一天的时间轴。
8. 修改、移动、删除或重新生成时间轴事件。
9. 区分计划内容和实际完成内容。
10. 标记事件已完成、未完成、跳过或实际内容不同。
11. 完成饮食、训练、工作、学习及其他事件记录。
12. 查看和修改历史记录。
13. 使用完整的减脂 Mode。
14. 达到可以正常每日使用并正式发布为 v1.0 的状态。

完整流程：

`公共食品数据库 → 每日分类与需求设置 → 下一周规划 → 每日时间轴自动生成 → 执行计划 → 实际完成记录 → 历史查看`

### v0.2.1：公共食品数据库

核心目的：

- 导入常见食品信息并统一设置为公共食品。
- 让用户不需要从空食品库开始使用。
- 完善公共食品和个人食品的数据结构、权限及历史快照。
- 支持食品搜索、新增、编辑、停用和正常使用。

### v0.2.2：整体记录功能完善

核心目的：

- 完善饮食、训练、工作、学习及其他生活事件的记录能力。
- 支持新增、修改、删除、补录和历史查看。
- 保证所有记录都可以正确保存并按用户隔离。
- 建立统一时间轴事件基础，为规划和后续多 Mode 扩展做准备。

### v0.2.3：每日分类与活动需求选择

核心目的：

- 让用户为未来每一天选择工作、学习、训练、休息或自定义类型。
- 填写当天的工作时间、学习时间、训练时间、起床、睡觉、通勤及其他重要事件。
- 选择用餐次数、训练安排和其他规划需求。
- 固定事件在自动生成计划时不能被随意覆盖。

食物模板不作为独立版本，只作为食品选择和自动规划中的辅助能力，根据实际需要轻量实现。

### v0.2.4：下一周规划界面

核心目的：

- 建立统一的未来七天规划界面。
- 用户可以分别设置每一天的类型、活动、固定事件和需求。
- 支持复制某一天或某类日期的设置。
- 用户只需要填写关键事件和需求，不需要手动建立完整时间轴。

### v0.2.5：每日时间轴自动生成

核心目的：

- 根据每日分类、固定事件和用户选择的需求，自动生成未来一周每天的时间轴。
- 自动安排饮食、训练、工作、学习、通勤、休息和其他相关事件。
- 固定事件不得被自动生成内容覆盖。
- 用户可以修改、移动、删除、锁定或重新生成结果。
- 重新生成时应尽量保留用户已经确认或锁定的内容。

当前阶段使用明确规则完成生成，不要求依赖 AI。

### v0.2.6：计划与实际完成记录

核心目的：

- 明确区分“原计划”和“实际发生”。
- 每个时间轴事件支持以下状态：
  - 计划中。
  - 已完成。
  - 未完成。
  - 跳过。
  - 实际内容与计划不同。
- 用户可以修改实际时间、实际食品、实际克重及实际事件内容。
- 支持添加计划外事件。
- 历史记录同时保留原计划和实际执行结果。

同时支持快速确认：

- 当实际内容与计划一致时，可以直接将计划标记为完成。
- 不要求用户重复填写相同内容。
- 为后续“一键完成主要记录”的体验优化预留结构。

### v0.2.7：减脂 Mode

核心目的：

建立能够正常实际使用的减脂记录与规划模式，作为 v1.0 必须具备的核心 Mode。

至少包括：

- 设置每日热量目标。
- 设置蛋白质、脂肪和碳水目标。
- 支持训练日和休息日使用不同目标。
- 显示计划摄入。
- 显示实际摄入。
- 显示当天剩余热量和营养目标。
- 记录体重。
- 将减脂需求用于一周计划和每日时间轴生成。
- 保留计划目标与实际完成结果。

减脂 Mode 不能只作为名称或空入口，必须形成可以实际使用的基本闭环。

### v0.2.8：v1.0 发布验收

核心目的：

完成全部功能整合、测试、性能检查、历史数据安全检查和正式上线准备。

v0.2 只有在以下条件全部满足后，才可以升级为 v1.0：

- 公共食品数据库已经导入并可用。
- 整体记录功能完整。
- 下一周规划可以正常使用。
- 每日时间轴可以自动生成。
- 计划与实际完成情况可以正确保存。
- 减脂 Mode 可以正常使用。
- 普通用户、管理员和多账号权限正确。
- 历史数据不会因食品、计划或模板修改而被破坏。
- 核心自动化测试和数据库测试通过。
- Production 已部署正确的数据库 Migration。
- 修改意见和建议历史已经完成上线前 Review。
- 版本更新日志已经根据实际改动更新。
- 本地、远程和 Production 版本一致。
- 正式上线后更新版本号为 `v1.0`。

## 4. v1.x：记录效率与用户体验优化

### 核心定位

v1.0 发布后，v1.x 不再补做 v0.2 遗留的核心功能，而是持续优化现有记录和规划体验。

长期体验目标：

> 让用户使用最少的操作和最短的时间完成每日记录。

重点方向：

- 最近使用。
- 常用内容。
- 复制上一餐或昨天记录。
- 快速调整数量。
- 一键确认单个事件。
- 一键确认整餐。
- 批量确认当天计划。
- 默认将计划内容作为实际内容。
- 用户只修改与计划不同的部分。
- 最终允许用户通过一个主要操作完成当天大部分记录。

“一键完成全部记录”应建立在已经生成并由用户确认的计划基础上，不应在没有确认的情况下自动伪造实际记录。

## 5. v2.0：多 Mode 生活记录平台

### 核心定位

从整体记录规划工具扩展为模块化的生活记录平台。

计划逐步加入：

- 身体健康 Mode。
- 健身 Mode。
- Financial Mode。
- 工作学习 Mode。
- 其他生活 Mode。

所有 Mode 应共享统一的：

- 时间轴。
- 计划与实际。
- 完成状态。
- 目标。
- 历史记录。
- 模板或规则。
- 用户权限和数据访问层。

不要为每个 Mode 重复建立一套互相独立的记录系统。

## 6. v3.0：离线优先与 App 化

### 核心定位

让软件可以在手机端和无网络环境下稳定使用。

主要方向：

- 本地数据库。
- 离线记录。
- 本地缓存。
- 云端同步。
- 数据冲突处理。
- 备份与恢复。
- 手机 App 化。
- 移动端快速记录入口。

从当前阶段开始，数据访问结构需要保持模块化，避免页面永久直接依赖 Supabase，为未来离线化保留迁移空间。

## 7. v4.0：AI 个人助手

### 核心定位

在已经积累稳定记录、规划和多 Mode 数据后，引入 AI 辅助用户规划和记录。

主要方向：

- 自然语言新增和修改记录。
- 自动生成或调整计划。
- 根据历史执行情况优化下一周安排。
- 总结饮食、训练、健康和财务变化。
- 发现遗漏、异常和长期规律。
- 用户确认后执行 AI 建议。

AI 不应替代底层明确的数据结构和规则系统。

## 8. v5.0：个人知识数据库

### 核心定位

将用户长期的记录、计划、偏好、文档、决策和结果连接为可搜索、可追溯、可被 AI 使用的个人知识系统。

主要方向：

- 统一个人档案。
- 关联食品、事件、目标、计划和历史结果。
- 保存用户习惯和偏好。
- 关联不同 Mode 的长期数据。
- 支持自然语言搜索个人历史。
- 所有回答可以追溯至对应数据来源和时间。
- 为长期个人知识助手提供数据基础。

## 9. 统一长期原则

1. **先完整可用，再追求智能。**
2. **v0.2 的全部确认功能必须在 v1.0 前完成。**
3. **从 v1.x 开始持续减少用户记录所需的点击、输入和时间。**
4. **计划与实际必须分开保存。**
5. **历史数据不能因模板、食品或规则修改而被破坏。**
6. **所有 Mode 共享统一的事件和数据基础。**
7. **离线、AI 和知识数据库是现有系统的逐步增强，不是重新开发独立软件。**
8. **位置感知目前不作为明确版本重点，只保留为未来可重新评估的方向，不在当前 Roadmap 中详细展开。**
