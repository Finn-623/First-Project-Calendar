## 已知问题与上线风险

- `auto-archive-records` 本地源码已增加独立服务端 Secret 鉴权：无 Authorization 返回 `401`，错误密钥返回 `403`，且鉴权通过前不创建数据库客户端。`verify_jwt=false` 仅用于允许 Cron 使用独立 Bearer Secret，而不是终端用户 JWT。
- 生产部署前必须创建 Supabase Secret `AUTO_ARCHIVE_CRON_SECRET`，部署函数后把 Cron POST 请求改为 `Authorization: Bearer <secret>`。Cron 侧值必须来自 Vault 或服务器 Secret 管理，不能硬编码到 SQL、前端或仓库。
- 本地没有 Deno／Supabase CLI，尚未在真实 Edge Runtime 和生产数据库执行集成测试。部署后需用隔离账号验证：无密钥 401、错误密钥 403、正确密钥可执行、未到时间不删除、只归档前一日目标数据，以及写归档或删除异常时不会发生无归档的数据删除。
- 自动归档已改由迁移 `020_auto_archive_transaction.sql` 提供的 `auto_archive_user_records` RPC 完成：advisory lock 串行化同一用户日期，表锁阻止快照与删除之间出现新写入，资格复核、快照 upsert、时间轴删除和唯一防重日志均处于同一数据库事务，任一步异常整体回滚。
- 迁移 020 后续加固已移除全表锁：只对目标用户/日期的现有 `timeline_items`、关联 `food_entries` 和对应归档行使用行锁，并只删除本次已写入快照的 ID；读取后新插入的记录不会被本次调用误删。
- 迁移 015 只替换仓库明确命名的三项 policy，不再遍历删除未知生产 policy；迁移 016 不再把缺少完成版本的历史 completed 数据重置为 pending，而是保留 completed 和 completed_at，允许 legacy `completed_version` 暂时为 NULL。
- 重复 Cron 调用会先命中 `(user_id, archive_date)` 唯一日志并返回 `already_processed`；并发调用被同一 advisory lock 串行化。事务提交前异常不会留下“只写归档”或“只删除时间轴”的部分状态，Cron 可安全重试。
- 上线前只读预检位于 `supabase/preflight/v0.1.2_migrations_014_020_readonly.sql`；当前未连接任何生产或隔离数据库，预检结果和真实迁移执行仍待人工完成。
- 无法从本地仓库确认迁移 `011`–`020` 已按顺序应用到生产环境；迁移 020 未应用前，新版 Edge Function 的 RPC 调用会失败，因此必须先迁移、后部署函数、最后启用 Cron。
- 无可用的普通用户／管理员双账号和生产环境访问，本次无法完成真实登录、账号切换、跨用户隔离和移动端真机回归。
